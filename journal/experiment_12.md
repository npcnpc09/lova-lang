# Experiment 12 — Abstraction and iteration (M9)

**Date:** 2026-09-09
**Script:** `experiments/experiment_12_abstraction.py`
**Status:** Done. **WIN on expressiveness / PARTIAL on ceilings / NULL — in fact negative — on density.**

## Hypothesis

H1. LOVA before M9 was not computationally universal, and this was a
hard ceiling rather than a missing convenience: with `LAMBDA` and
`APPLY` raising `NotImplementedError`, `LOOP_UNTIL` unimplemented and
`LET` a plain let, a program could not name a function, call one, or
repeat anything. Every task requiring recursion or iteration should
therefore be *unrepresentable*, not merely awkward.

H2. Unary closures + currying + letrec + a loop combinator lift that
ceiling without spending a single new token, because 0x2B/0x2C/0x2D
were already declared with the arities those semantics need.

H3. Once non-termination is reachable it must stay inside the error
model: every runaway program produces a structured anomaly carrying
the L2 schema, never a hang and never a Python traceback.

H4. The density advantage measured in Exp 07 / Exp 11 generalises to
algorithmic tasks.

## Method

Ten tasks that cannot be written without abstraction — factorial,
fibonacci, is-prime, collatz-steps, sum-to, power-of-two, gcd by
Euclid, count-divisors, multiply-by-adding, divide-by-subtracting —
each checked against a Python reference across 3–7 inputs (44 cases
total). The pre-M9 baseline is *measured*, not assumed: each program
is re-walked against the operator set the pre-M9 runtime implemented.

Universality is demonstrated by exhibiting the μ-recursive basis:
zero test (`if-surprise`), successor and predecessor (`merge` with
±1), composition, primitive recursion (factorial), and unbounded
minimisation (`loop-until` computing `μx. x² ≥ n`, checked on 7
inputs).

Ceilings: five runaway shapes — three recursive, two looping — each
run and inspected for trap class and anomaly completeness.

Density: bytes of the encoded integer form, plus `tiktoken`
`cl100k_base` counts of the Stage-1 text surface, against idiomatic
Python for the same ten algorithms. The Stage-2 estimate uses Exp 11's
method exactly (one token per AST node plus one per literal payload).

Deliberately **not** number-theory tasks. Exp 07 and Exp 11 measured
density on a corpus where LOVA has a one-byte built-in (`p`, `τ`, `σ`,
`μ`) and Python calls sympy. These ten have no shortcut on either side.

## Results

| Measure | Result |
|---|---|
| Tasks passing under M9 | **44 / 44 cases**, 10 / 10 tasks |
| Tasks representable pre-M9 | **0 / 10** |
| μ-operator via `loop-until` | 7 / 7 inputs correct |
| μ search under `max_call_depth=4` | correct — iteration consumes no call frames |
| Runaway shapes trapped | **5 / 5** (3 `DepthTrap`, 2 `StepTrap`) |
| Traps carrying the full L2 schema | **5 / 5** |
| Bytes, LOVA vs Python | 654 vs 775 → **1.19×** |
| Stage-1 LLM tokens, LOVA vs Python | 471 vs 312 → **0.66×** |
| Stage-2 estimate vs Python | 480 vs 312 → **0.65×** |

New tokens spent to get all of this: **zero**. `mul` and `mod` took
over 0x0B / 0x0C — the mock-theta φ₃ / ψ₇ slots, which had carried a
name and an arity since M1 and never a line of implementation.
`deviation` (0x1F) and `threshold` (0x1B) were likewise already
declared in the surprise family. The core is still 64 operators;
runtime-implemented went **18 → 25**.

(The 19 quoted in the README, `CLAUDE.md` and the old `spec/tokens.md`
was already off by one — `TYPED_TOKENS` held 18 before M9. The token
spec is now generated by `spec/generate_tokens_md.py` rather than
transcribed, so the count cannot drift again.)

Test suite: 122 → 188, all passing.

## Findings

**F1. The pre-M9 ceiling was total, not partial.** 0/10. Not one of
the ten tasks could be *written*, let alone written badly. Everything
in `corpus/` and `apps/` before this milestone was a fixed-depth
expression over built-ins, which is why LOVABench's 60 tasks are all
one-shot compositions: the corpus was shaped by what the language
could say. This matters for M8 — a fine-tuning corpus generated from
the pre-M9 language would have taught a model a sublanguage of
straight-line arithmetic and called it a programming language.

**F2. The token table had room for all of it.** 0x2B/0x2C/0x2D were
declared arity 2 / 2 / variadic in M1. Unary lambda + currying fits
arity 2 exactly; `loop-until` as a *combinator* returning a function
(rather than a statement) fits arity 2 exactly; `apply` needed only a
typed head slot on the existing variadic. Axiom 8's ≤64 bound was
never the constraint people assume it is — the constraint was that
nobody had tried to write a program.

**F3. Recursion needed one semantic change, and it was
backward-compatible.** `LET` became a letrec. Before M9 a
self-reference in a value slot was an `unbound-ref` *compile error*,
so the set of programs that used to compile is untouched; the change
strictly widens it. No axiom moved.

**F4. The type system needed a top type, and that exposed a real
hole.** A binding may hold an integer or a function, so `LET`'s value
slot became the language's one `Value` slot. `REF` still declares
`Int`, because `valid_next` cannot consult scope — name ids live in
LIT_INT payloads, which the generation state machine never sees. So
`(merge (ref f) 1)` where `f` holds a function is caught by the
*compiler* (a scope-aware type environment was added for exactly
this), not by generation. That is the same division of labour Exp 08
established for `unbound-ref`, so it is consistent — but it means
Axiom 3's "ill-typed programs are not representable" holds at the
operator level and not at the name level. This should be stated that
precisely wherever the axiom is quoted.

**F5. Ceilings work, and one of them is doing more than expected.**
5/5 runaway shapes trapped with a complete anomaly. Making `DepthTrap`
and `StepTrap` subclasses of `BudgetTrap` means every existing handler
covers them for free. `MAX_STEPS` also turned out to be the backstop
that catches a `loop-until` whose predicate is never satisfied —
call-depth accounting alone would have hung, because the loop
combinator deliberately iterates instead of recursing.

**F6 (negative). The density claim does not survive contact with
algorithmic tasks.** On tasks where neither side has a built-in
shortcut, the Stage-1 surface costs **1.5× more LLM tokens than
Python** (0.66×), and the Stage-2 projection does not rescue it
(0.65×). The byte-level number stays mildly positive (1.19×) but is
nothing like 39×.

The mechanism is not subtle. `(merge n -1)` is 7 tiktoken tokens
against `n - 1`'s 3. `if-surprise` is not a cheap word. Where the
README reports 8.5×, the LOVA program is `(sigma n)` and the Python is
three lines of sympy import and call; the ratio was measuring the
built-in library, not the language. Both numbers are real; they answer
different questions, and only one of them is about writing programs.

**F7. Stage-2 does not fix F6, which is informative.** The Stage-2
estimate is *worse* than Stage-1 here (480 vs 471 tokens). AST node
count is dominated by the arithmetic scaffolding — `(merge n -1)` is
five nodes for what Python spends one operator on — so a denser
*vocabulary* cannot help; only a denser *encoding of arithmetic* can.
That points at the operator set rather than at the tokenizer.

## Discussion

F1 and F2 together read as a process finding more than a technical
one. The language shipped ten experiments, a 60-task benchmark, a
compiler, a telemetry DB and two apps before anyone tried to write
`factorial`. Each of those artifacts is real work and none of them
needed abstraction, so nothing surfaced the gap. The corpus in
particular is self-confirming: tasks were authored in the language, so
they only ever exercised what the language had.

F6 is the finding that should change decisions. The pitch rests on
density, and density measured on "tasks with a matching built-in" is
close to circular — the eight number-theory operators are a standard
library rendered as opcodes, and the comparison credits the language
for the library. The honest split:

- LOVA is dense **where its built-ins match the task**. Real, and a
  legitimate design argument for a domain-shaped operator set.
- LOVA is **less** dense than Python for general algorithmic code, at
  Stage 1 and under the Stage-2 projection alike.

F7 says the lever is arithmetic surface, not tokenizer. LOVA spends
`(merge n -1)` where Python spends `n-1`; there is no `div`, so
division is O(a/b) repeated subtraction; there is no `<`, so ordering
is a two-operator idiom. Those are operator-table decisions.

Which raises the question the table itself poses: eight of 64 slots go
to number theory (`p`, `τ`, `σ`, `η`, `gcd`, `μ`, plus the two just
reclaimed), and none went to `div`, `<`, or a pair/list type. That
allocation was made before any program existed to justify it. It is
worth re-deriving now that ten do.

The universality demonstration is deliberately modest. Exhibiting the
μ-recursive basis is an observation about the operator set, not a
proof of Turing-completeness; a machine simulation would be the next
rung and is not claimed here.

## Next questions raised

- **Q30.** Exp 03 and Exp 07 no longer run — `CLAUDE_SOLUTIONS` and
  `PYTHON_SOLUTIONS` cover only the 20 v1 tasks while `TASKS` is now
  the 60-task v2 set. This predates M9 (verified against the pre-M9
  tree). The README's headline correctness number (20/20 vs 19/20)
  currently has no runnable script behind it.
- **Q31.** Should the number-theory family give up more slots?
  `div` and a comparison operator would remove the two costliest
  idioms F7 identifies. What is the actual density gain, measured?
- **Q32.** Is there a terser Stage-1 surface that closes F6 without
  touching semantics — infix or APL-style projection over the same
  tokens? F7 suggests the answer is mostly no, but it is measurable.
- **Q33.** Should LOVABench v3 include an algorithmic category? The
  present 60 tasks cannot express recursion, so the benchmark cannot
  currently detect a regression in it.
- **Q34.** Mutual recursion is not expressible: a `defn` sees earlier
  definitions and itself, never later ones. Does a letrec\* group form
  earn its keep, or is source ordering an acceptable constraint?
- **Q35.** Partial application is statically unchecked — `Fn` does not
  track curried arity, so `(merge (apply f 3) 1)` type-checks and
  fails at run time when `f` takes two arguments. Does an arity-indexed
  `Fn<n>` pay for itself?
- **Q36.** `constrained_random` can now emit lambdas, so Exp 03's
  well-formedness rates and Exp 10's telemetry DB are measured against
  a different token distribution than when they were recorded. Both
  need a re-run before their numbers are quoted again.

## Status

LOVA can express recursion, iteration and user-defined functions for
the first time (44/44 cases, from 0/10 representable), spending no new
tokens and moving no axiom — and the same experiment shows the density
claim reverses on tasks that have no built-in shortcut, which is the
number that matters for the language's actual pitch.
